## Problem Statement

我每天收盘后要自己翻一遍关注的股票，判断哪只出现了值得看的变化：是不是突破了、是不是放量了、是不是跌到某个位置。这件事耗时，而且容易漏——漏掉的那只往往就是后来涨起来的那只。家里跑着的 `lianghua` 只有行情数据和一批扫描脚本，它不告诉我「今天有什么变了」，也不记得「这只上周已经提醒过了」。

我也需要人在外面的时候能知道这件事。手机连着家里的网络时还好，一旦离开就什么都收不到。

## Solution

一个只读行情的分析平台：在 Web 上维护**自选**、配置**规则**；服务端每个交易日收盘后对自选范围内的规则求值，只在「不满足 → 满足」的那一刻产生一条**预警**；预警通过 ntfy 推到手机，通知体自带触发时的关键数据，不打开 App 也能判断；邮件作为兜底。没被推送的命中项合并进当日的**日报**。

Android 端只做消费：看预警列表、看触发快照，个股详情交给浏览器打开 Web。

## User Stories

1. 作为使用者，我要能配置行情数据目录，以便把数据放在我指定的磁盘位置而不用改代码。
2. 作为使用者，我要能一次性灌入历史日 K，以便规则求值有足够的历史窗口。
3. 作为使用者，我要能按交易日增量更新行情，以便每天只拉新增数据、失败后能重跑。
4. 作为使用者，我要在取数失败时看到明确的错误与失败的日期区间，以便知道该补哪一段，而不是面对一个静默的空结果。
5. 作为使用者，我要能搜索并添加股票到自选，以便划定我关心的范围。
6. 作为使用者，我要能从自选里移除股票，以便范围始终是我想看的那些。
7. 作为使用者，我要在自选列表看到最新收盘价与涨跌幅，以便一眼扫过。
8. 作为使用者，我要能打开个股详情看日 K 与均线，以便判断预警是否值得细看。
9. 作为使用者，我要能新建一条规则（突破 / 超跌 / 放量 / 均线），指定标的范围、指标、阈值与时间窗，以便让系统替我盯。
10. 作为使用者，我要能修改和停用规则，以便阈值不合适时随时调整。
11. 作为使用者，我要规则在收盘后自动求值，以便第二天早上就有结果。
12. 作为使用者，我要同一条规则在同一只股票上连续满足时只收到一次预警，以便通知不被同一件事刷屏。
13. 作为使用者，我要在条件回落后再次满足时能重新收到预警，以便真出现第二次机会时不被我错过。
14. 作为使用者，我要每天收到的推送有数量上限，超出的进入日报，以便通知始终保持可信。
15. 作为使用者，我要通知体里直接看到标的、规则、触发价、阈值与数据日期，以便在外面没有网络访问服务端时也能判断。
16. 作为使用者，我要推送失败时通过邮件收到同样的内容，以便不漏消息。
17. 作为使用者，我要在 App 里看到预警列表，并区分已读与未读，以便知道哪些还没看。
18. 作为使用者，我要在 App 里点开一条预警看到触发快照，以便了解当时的具体数值。
19. 作为使用者，我要能从预警详情跳转到浏览器打开该股的 Web 详情页，以便在手机上也能做进一步分析。
20. 作为使用者，我要每天收到一份日报，包含当天触发的预警与接近阈值的观察项，以便掌握全貌而不被逐条推送打扰。
21. 作为使用者，我要在 Web 上回看历史预警与日报，以便复盘某条预警后来是否灵验。
22. 作为使用者，我要在重复求值同一天时不产生重复预警，以便数据重灌或重跑后记录不乱。

## Implementation Decisions

**项目边界**

- 新建 `quant/` 作为第三个独立项目，与 `lianghua/`、`everything/` 并列；不复用对方的运行产物，不改动根 `AGENTS.md` 的边界规则。
- 行情数据目录由配置提供，不硬编码；不使用 `lianghua` 的 Parquet 数据文件。

**数据层**

- **不复用 `lianghua` 的存储实现代码**，只沿用其列 schema 与设计思路，导入与读写逻辑自行实现。存储粒度见 ADR 0004。
- 内部统一代码格式为 `sh.600000` / `sz.000001`（与数据源一致），导入时把其他写法归一。
- **落盘字段**：不复权 OHLCV + 每行**前向填充后的 `back_factor`**。不落盘任何复权后的价格列。后复权价 = 原始价 × 该行 `back_factor`（一次乘法，不需跨行累积）。
- **只计算后复权，完全不计算前复权**：前复权以最近一次除权为基准、每次新除权都会改写全部历史，既不落盘也不提供；展示用不复权价，跨日价格比较与指标计算统一用后复权价。
- **不存后复权价的原因**：后复权价是派生数据，落盘后真实价不可逆（展示与通知需要真实价），且源站修正历史因子时整条历史价格都无法局部修复；而存原始价 + 因子只改一行即可。
- 历史日 K 源：每个交易日一个 UTF-8（含 BOM）CSV，全市场横截面，18 列固定 schema：`date, code, open, high, low, close, preclose, volume, amount, adjustflag, turn, tradestatus, pctChg, peTTM, pbMRQ, psTTM, pcfNcfTTM, isST`。
- 历史因子源：每日一个 CSV，列 `code, dividOperateDate, foreAdjustFactor, backAdjustFactor, adjustFactor`；内容为**当日发生除权的标的清单**，不是全市场快照（样例：2025-02-14 共 3 行，2026-06-12 共 92 行，行数随分红季波动）。未发生除权的标的不出现，读取时按「无记录即因子为 1」处理。
- **后复权因子以官方每日清单为准**：`bs.query_daily_adjust_factor(date=...)` 按日一次返回当日全部除权标的的 `backAdjustFactor`；日 K 推导（`因子(t) = 因子(t-1) × 昨日不复权收盘 ÷ 当日 preclose`）作为校验与兜底，两者不一致时以官方值落库并记录告警。
- **每日增量只需两次按日批量调用**，不按标的循环：
  - 日线：`bs.query_daily_history_k_AStock(date=...)`，一次返回全市场 A 股当日 18 列
  - 因子：`bs.query_daily_adjust_factor(date=...)`，一次返回当日全部除权标的的 5 列（无除权则为空表）
- **指数不在上述批量接口覆盖范围内**（样例日线文件中不含 `sh.000001` 等指数代码），指数日线需用 `bs.query_history_k_data_plus(code, "date,code,open,high,low,close,preclose,volume,amount,pctChg", ..., frequency="d", adjustflag="3")` 单独逐只获取，数量为个位数。
- 因子的自检：单次除权带来的因子增量落在 `[0.5, 3]` 之外时告警。A 股最极端的送转加分红其比值约 2 出头，超出该区间基本可判定为 `preclose` 数据错误。
- **因子只入后复权因子**（ADR 0005）：前复权因子会随新除权被追溯改写，因此不入库、不计算、不对外提供。
- 停牌处理：停牌标的**仍在横截面文件中**（`tradestatus=0`），其 `close` 等于 `preclose`、`volume` 与 `amount` 为空。规则求值必须显式排除停牌行，否则量比与均线会被无效数据污染；因子推导中停牌行比值为 1，可安全通过。
- 导入校验：同一标的的后复权因子必须单调不减，否则视为数据异常并报错。
- 跨日价格比较统一使用后复权序列（原始价 × 当日后复权因子）。
- 历史一次性导入：以按日横截面文件为源，做代码规范化、按年份聚合、按 (标的, 日期) 排序后落盘，并产出 manifest（行数、日期范围、缺失交易日、重复行、因子缺失的标的）。
- 存储粒度为「年份单文件」（每年一个 Parquet，含当年全市场），每日增量重写当年文件并原子替换；详见 ADR 0004。
- 查询层使用 DuckDB 直接读 Parquet，不引入独立的时序数据库。
- 每日增量拉取**全市场**（两次按日批量调用 + 指数逐只），不做按标的筛选；写入时按 (标的, 日期) 去重并原子替换当年文件，重复执行同一交易日为覆盖而非追加。
- 修复型重算：当某标的的复权因子与已存值不一致（除权导致）时，只重算该标的，不触发全量重建。
- 交易日以行情中实际存在的日期为准，不额外引入交易日历依赖。
- 增量游标保存在状态文件中，记录最后成功交易日；失败日期留缺口，下次运行自动补齐。
- 每次取数产出运行记录：日期区间、成功数、失败标的、耗时，失败必须可见。

**规则与触发**

- 规则 = 标的范围 + 指标 + 阈值 + 时间窗；P0 支持突破、超跌、放量、均线四类。
- 放量与缩量统一用「量比」表达：当日成交量 ÷ 前 N 日均量，均值**不含当日**，N 默认 5；放量阈值默认 1.5，缩量阈值默认 0.6，均按规则可配。不含当日是为了避免当日放量把均值一起抬高、导致阈值失效。
- 突破、超跌、均线均以**后复权收盘价序列**计算，全部为相对指标。P0 不接受绝对价格阈值，避免后复权价与真实价位的换算问题。
- 日涨跌幅规则直接使用源字段 `pctChg`，不用 `close ÷ 前一日 close` 自算：`preclose` 在除权日已是调整后昨收，自算会在除权日产生假暴跌误报。
- 量比不涉及复权，直接使用原始成交量。
- 求值按交易日进行，只在收盘后执行；不做盘中求值。
- 触发是边沿语义：每个「标的 + 规则」维护触发态与最近触发日期，仅在状态由「不满足」转为「满足」时产出预警。
- 预警的唯一性由「标的 + 规则 + 交易日」保证，重复求值不重复产出。
- 每日推送条数设上限（默认 10），超出部分不推送、进入日报。
- 日报含「接近阈值」项：条件已满足但未达阈值，且与阈值的相对差距在 20% 以内（例如放量阈值为 1.5 时，量比 ≥ 1.2 即计入）。

**通知**

- 通知做成接口，P0 有两个实现：ntfy 与邮件；推送失败时降级到邮件。
- 通知内容包含：标的代码与名称、规则名称、触发值、阈值、数据日期，保证脱离服务端也可读。
- 日报走同一套通知接口（ntfy + 邮件兜底），每个交易日收盘求值后生成一份，不依赖是否产生预警。

**接口**

- 统一 `/api/v1` 前缀，JSON 字段使用 camelCase，时间为 ISO 8601；沿用仓库既有的跨项目协议约定。
- 无鉴权、单用户。

**客户端**

- Web 端负责配置与回看：自选管理、规则配置、预警记录、日报、个股详情（日 K + 均线）。
- Android 端只做两页：预警列表（已读/未读）、预警详情（触发快照）；个股详情跳转浏览器。
- App 在无法访问服务端时不得反复重试失败请求，需明确呈现离线状态。

## Testing Decisions

**Seam 一：规则求值器（纯函数）**

- 输入是行情切片与规则定义，输出每条规则的满足与否及触发结果。
- 用固定 fixture 行情验证：首次满足产生触发、连续满足不重复触发、回落后再次满足重新触发、同日重复求值幂等。
- 只测外部行为：给定输入得到什么结果，不测内部状态字段如何命名。

**Seam 二：HTTP API（TestClient）**

- 验证自选增删查、规则创建与停用、预警列表已读未读切换、日报生成的响应行为。
- 不通过 HTTP 层重复验证规则数学逻辑，那是 seam 一的职责。

**其他**

- 数据源适配器不作为测试 seam，测试中用假数据替换；真实 baostock 调用只在手工验证时使用。
- 测试框架使用 pytest，与仓库既有的 Python 项目一致；prior art 为 `lianghua/tests/` 下的 `test_ingest.py`、`test_datasource_factors.py`、`test_baostock_reconnect.py`、`test_market_api.py`（仅借鉴测试组织方式与 fixture 写法，不复用其代码）。

## Out of Scope

- 交易、持仓、收益统计、做T（属于 `everything/`，本产品显式不含持仓概念）。
- 盘中实时行情与实时预警。
- 多用户、登录、权限、配额。
- 条件选股器、策略回测、多因子研究。
- 第二数据源、基本面、资金流、财务数据。
- Android 端的自选页、个股详情页、规则配置页。
- iOS 端。
- 公网部署、隧道、厂商推送 SDK。

## Further Notes

- 存储与导入逻辑自行实现，不复用 `lianghua` 的实现代码，因此不存在「两份副本需要同步」的问题；代价是两边 schema 会逐渐分叉，不能期望将来能合并。
- 因子填充的边界（长期停牌后复牌）需在实现时自行确定 `ffill` 语义；baostock 官方文档第六步的具体实现尚未核对到。
- ntfy 主题名必须是足够长的随机串，因为知道主题名即可订阅；消息经第三方中转。
- 历史数据需要一次性重灌，属于上线前的一次性动作，不在每次部署中重复。
- 页面与通知均需包含「仅为数据分析、不构成投资建议」的提示。
- 数据源为 baostock 免费接口，历史上存在会话失效与连接中断，取数层需要显式重登与失败上报。
