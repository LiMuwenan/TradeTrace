# 0001 新产品 quant/ 的目录边界与数据层复用范围

- 状态：已接受
- 日期：2026-11-16

## 背景

要做一个「股票量化数据分析 + 预警」平台，含 Web 端与 Android 端，**不做交易**。决定不再在既有的 `lianghua/`、`everything/` 上迭代，但继续留在同一个仓库。

根 `AGENTS.md` 已规定：两个既有项目独立构建运行，禁止跨项目 import 源码、禁止直接读写对方的数据库与行情文件；一切交互只通过显式 HTTP 接口。

`lianghua` 的现状：数据源只有 baostock，仅日 K、复权因子、指数日线；存储为按股票一文件的 Parquet；`scanner.py` 是策略 manifest 扫描器，不是预警引擎。

## 决策

1. 新产品落在 `quant/`，与 `lianghua/`、`everything/` 并列，作为第三个独立项目。
2. 数据目录**独立且在配置中指定**，不硬编码；历史数据重新灌入。
3. ~~复用 `lianghua` 的 Parquet 存储实现（`parquet_store.py`、`index_store.py`），以复制方式引入。~~ **已修订**：只沿用列 schema 与设计思路，存储与读写代码自行实现，不做复制。原因见「修订记录」。
4. **重写 baostock 取数逻辑**。动因是既有实现质量差、难维护、错误处理不清晰，因此新实现的验收重点是可读性、失败可见、可重跑。
5. 技术栈：后端 Python / FastAPI；Web 端 Vue 3；Android 端 Expo / React Native。

## 备选方案

| 方案 | 未采用的原因 |
|---|---|
| 新建独立仓库 | 要重建 CI、AGENTS.md 等基建；仍想保留对旧实现的参照 |
| 直接 `import lianghua` 的代码 | 违反根 `AGENTS.md` 的项目边界 |
| 完全重写数据层 | Parquet 的列 schema（含复权因子与估值）是资产，重写会重踩复权与估值的坑 |
| 直接读 `lianghua` 的 Parquet 目录 | 仍属「直接读对方行情文件」；会让「哪份数据是权威」永久模糊 |
| 把数据层抽成共享 Python 包 | 过度设计，等新产品跑起来再评估 |

## 后果

- 列 schema 在 `lianghua` 与本项目各有一份定义，变更时需要人工同步（仅剩 schema 层面的耦合）。
- 需要一次性重灌历史数据。
- 前端存在 Vue 与 React Native 两套技术栈，但两端都有现成参照物。
- 后端已锁定 Python；若将来改语言，复用的存储实现与取数逻辑都要重写。

## 修订记录

- 2026-11-16：原决策 3（复制 `parquet_store.py` / `index_store.py`）撤销。原因有二：一是存储粒度改为「标的 + 年份」分区（见 ADR 0004），复制来的实现已无法与 `lianghua` 保持同步；二是历史数据源是用户自有的按日横截面 CSV，导入逻辑本来就是新写的。改为只沿用列 schema 与设计思路。
