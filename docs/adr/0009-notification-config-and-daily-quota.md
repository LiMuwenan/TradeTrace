# 0009 通知配置落 meta.db，每日上限按「交易日 + 尝试条数」计数

- 状态：已接受
- 日期：2026-11-26
- 关联：ADR [0007](./0007-rule-state-event-stream.md)（用户记录落 `meta.db`）、ADR [0008](./0008-evaluate-invokes-notify.md)（求值末尾同步推送）

## 背景

08 号票要求「设置页可配置 ntfy 服务地址与主题、收件邮箱、每日上限开关」，还要求「每条通知的发送结果可查」。这两件事各带来一个必须先定的口径：

1. **通知配置写在哪**。项目原有的配置路径只有 `config/config.toml`（部署配置，随仓库版本管理），用户数据在 `{meta_dir}/meta.db`。设置页属于用户数据还是部署配置，票面没说。
2. **每日上限怎么计数**。票面只写「存在每日推送上限（默认 50 条），超出的预警只落库不推送」，没写按什么周期重置、数成功还是数尝试。

## 决策

1. **通知配置与投递记录都落 `{meta_dir}/meta.db`**，新增两张表：
   - `notification_config`：单行（`id = 1`），存 ntfy 服务地址与主题、收件邮箱、SMTP 主机与凭据、每日上限开关与数值。
   - `notification_log`：每次投递尝试一行，记 `event_id`、交易日、通道、结果（成功／降级／失败）、错误摘要、尝试时间。
2. **配置由设置端点读写，`config.toml` 里不放任何通知字段**。`config.toml` 保持「部署参数」定位，通知配置是运行时可由用户修改的用户数据。
3. **凭据明文存 `meta.db`，但接口不回显**。读取接口把主题名、密码等敏感字段替换为「已配置」布尔量；写入接口留空表示「不修改」，避免前端每次提交都要回传明文。
4. **每日上限按交易日重置，计「尝试投递的预警条数」**。计数来源是 `notification_log` 中该交易日的不重复 `event_id` 数；成功的、降级后成功的、失败的都算一次。
5. **超限的预警不标记 `pushed_at`**，继续留在库里由 07 的列表展示；次日重跑该交易日也不会绕过上限（上限是当日的）。

## 备选方案

| 方案 | 未采用的原因 |
|---|---|
| 通知配置写 `config/config.toml` | 设置页要改文件，需额外处理原子写入、热加载与「改坏了服务起不来」；且该文件被 git 跟踪，用户改动容易与部署脚本冲突 |
| 配置放环境变量、设置页只读 | 做不到票面要求的「设置页可配置」 |
| 上限按自然日重置 | 预警天然绑定交易日，按自然日会在周末与节假日空转重置，行为诡异：周六补跑周五的求值会得到一份全新的额度 |
| 上限只数「成功送达」的条数 | ntfy 整体故障当天会全部走邮件，只数成功数等于放弃上限，邮件通道反被无限量灌爆，正好违背上限初衷 |
| 投递结果只记在 `rule_state_event.pushed_at` 上 | 失败与重试没有痕迹，`pushed_at` 为空无法区分「没试过」和「试了三次都失败」 |

## 后果

- `meta.db` 从「规则 + 事件」扩展到「规则 + 事件 + 通知配置 + 投递记录」，仍是单文件、单进程、标准库 `sqlite3`，不引入数据库服务。
- 凭据的暴露面是「本机文件可读」，与放 `config.toml` 等价；换来的收益是设置页可改、无需重启。若将来要加密，只影响 `notification_config` 的读写层。
- 上限计数的语义是「一天最多打扰 50 次」，不是「一天最多成功送达 50 条」。手工重跑同一交易日时，已尝试过的预警不会重复占用额度，但也不会因此突破额度。
- 07 的列表需要能看到「未成功投递」的预警，这依赖 `pushed_at` 与 `notification_log` 两张表互相印证，08 的实现不能只写其一。
