# 0004 行情存储按「年份」单文件分区，每日只重写当年文件

- 状态：已接受
- 日期：2026-11-16
- 修订：2026-11-20（分区粒度由「标的 + 年份」改为「年份」）

## 背景

历史行情来自用户已有的按日横截面文件（每个交易日一份，覆盖全市场）。而规则求值的访问模式是按标的读时间序列（某只股票近 N 日）。

`lianghua` 的存储实现是「每只标的一个 Parquet 文件」。在这种粒度下，每新增一个交易日都要重写该标的的全部历史；反过来，若改成「每天一个文件」，读单只股票近 60 日就要扫 60 个文件。

实际数据量：约 5200 只标的 × 250 交易日 ≈ 每年 130 万行，20 年约 2600 万行，压缩后总量不到 1GB。

## 决策

1. Parquet 按 **年份** 分区：每年一个文件，内含当年全市场所有标的。
2. 文件内按 (标的, 日期) 排序写入，使 Parquet 的 row-group 统计能跳过无关数据块。
3. 历史数据一次性导入，导入时做代码规范化、按年份聚合、排序落盘。
4. 每日增量写入当年文件；按 (标的, 日期) 去重后原子替换（写临时文件再 rename）。
5. 复权因子按「不复权价 + 每行后复权因子」存储，不存前复权数据。
6. 增量游标与每次运行的成败记录落在状态与运行记录中，失败日期留缺口待补。
7. 查询层使用 DuckDB 直接读 Parquet，不引入独立数据库服务。

## 备选方案

| 方案 | 未采用的原因 |
|---|---|
| 每只标的一个文件（沿用 `lianghua` 粒度） | 每日增量要重写全部历史，写入放大随年份增长 |
| 每标的每年一个文件 | 文件数达十万量级；每日增量需重写当年全部标的文件（约 5200 个），仅文件打开开销就是分钟级 |
| 每个交易日一个文件 | 读取单只标的时间序列要扫大量小文件，规则求值变慢 |
| InfluxDB 等时序数据库 | 只有日线数据（每年 130 万行），用不到其高频写入、降采样、保留策略的长处，却要多维护一个服务与一套 tag/field schema；横截面查询也别扭 |

## 后果

- 文件数约等于年数（二十个上下），备份、迁移、原子替换都很简单。
- 每日增量重写当年单文件（约 40MB），耗时与文件数无关，年份增长不会让每日成本变高。
- 读单只标的时需在当年 130 万行内按标的条件过滤；依赖列裁剪与 row-group 统计，实测应在百毫秒量级，规则求值需通过基准测试确认可接受。
- 跨年窗口（如近 250 日）需要打开两个文件并合并，读逻辑不能假设单文件。
- 分区键一旦定下，后续改粒度需要全量重写；因为原始 CSV 已归档，重建不需要重新联网取数。
