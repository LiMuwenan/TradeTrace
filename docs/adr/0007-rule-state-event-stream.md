# 0007 触发状态以事件流表达，用户预警数据落 meta.db

- 状态：已接受
- 日期：2026-11-26
- 关联：ADR [0002](./0002-daily-edge-trigger-alert-model.md)（日频边沿触发）

## 背景

05 号票要求三样东西同时成立：记录每条「标的 + 规则」当前是否处于触发态、只在「不满足 → 满足」时产一条预警、且能查询「何时进入、何时解除」。

按原设想这是三份数据：触发态一个布尔、预警一张表、解除历史无处安放。`GLOSSARY.md` 原先也写成「触发态不是历史记录；历史触发以预警记录的形式存在」——但预警只记进入，解除没有任何载体，05 的验收标准第 7 条因此在数据模型上无法满足。

同时暴露存储缺口：`meta_dir` 下目前只有 `watchlist.json` 与 `stock_names.json`，都是「全量读、全量写、体积恒定」的小文件。预警记录是持续增长、需要按状态筛选与按时间倒序分页的数据，JSON 不再合适。

## 决策

1. **单表事件流 `rule_state_event`**，一次求值对一个 (标的, 规则, 交易日) 最多写一条，`event` 取 `enter` 或 `exit`，唯一键为三元组。日频求值下同一对规则一天内不可能既进入又解除，因此唯一键成立。
2. **预警不是独立的表，而是 `event = 'enter'` 的行**。推送状态（`pushed_at`、`push_channel`）与已读状态（`read_at`）是这一行的列，`exit` 行这些列为空。预警与状态变更只有一份数据，不会出现「预警有记录、状态没记账」的分叉。
3. **触发态不落库**。当前是否处于触发态 = 该 (标的, 规则) 最后一条事件是 `enter` 还是 `exit`，读取时推导。避免一个必须与事件流双写同步的布尔字段。
4. **存储：`{meta_dir}/meta.db`，SQLite（标准库 `sqlite3`），单文件、无服务进程**。开启 WAL；写操作串行，单用户场景足够。**注意与 `lianghua/data/meta.db` 无关**——同名纯属巧合，两者分属不同项目，根 `AGENTS.md` 禁止跨项目读写。
5. **规则定义也落同一 `meta.db`（表 `alert_rule`）**，避免规则与其状态分居两处存储。
6. **新规则启用时做静默回放**：从库内最早交易日逐日求值到启用前一日，只写事件流、不推送，这些 `enter` 行标记 `replayed = 1`。回放结束后该规则的状态与历史触发次数即为真实值。
7. **规则改参数或停用时写一条 `exit` 收尾**，`reason` 分别为 `rule_changed` / `rule_disabled`，新参数从次日重新起算。

## 表结构要点

`rule_state_event`：`code`、`rule_id`、`trade_date`、`event`、`value`（触发时指标值）、`threshold`、`price`（判定所用的后复权价）、`reason`、`replayed`、`pushed_at`、`push_channel`、`read_at`、`created_at`。

## 备选方案

| 方案 | 未采用的原因 |
|---|---|
| 继续用 JSON 文件存预警 | 需全量读入才能筛选分页，一年几千行后每次请求都要解析整个文件 |
| 预警写 Parquet 按年分区 | 列式格式改一条「已读」要重写整个年份文件，且会与行情索引混在同一套目录语义里 |
| 触发态、预警、解除历史拆三张表 | 三者是同一事实的不同视角，拆开后必须靠应用层保证同步，重跑与补数时极易不一致 |
| 单独存一个 `is_triggered` 布尔字段 | 每个 (标的, 规则) 的布尔必须与事件流同步更新，任何一次写入失败都会造成永久偏差，且无法自愈 |
| 新规则不做回放，直接以启用日状态起算 | 会把「今天恰好满足」当成新触发，历史频次也全部丢失 |

## 后果

- 需要一个初始化与迁移策略：P0 无历史数据，首次启动建表即可；此后改表结构需手写迁移脚本，不能靠删库重建（用户数据不可从行情重建）。
- 静默回放的成本与标的数量、历史长度成正比（100 只 × 1 年约 2.4 万次判定），首次启用规则时会有可感知的等待，需要给出进度或至少明确提示。
- `replayed = 1` 的记录必须被 07 列表默认排除、被 08 跳过推送，否则一次回放会炸出上百条历史通知。
- 「历史触发次数」与「真实提醒过几次」从此是两件事，统计口径需分别说明，不能混用。
