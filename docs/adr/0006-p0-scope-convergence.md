# 0006 P0 收敛为预警最小闭环，Android 推迟到 P1

- 状态：已接受
- 日期：2026-11-26
- 修订：ADR [0003](./0003-lan-deployment-and-ntfy-push.md) 决策 4 中「Android 只做两页」的交付时点

## 背景

`.scratch/quant-p0/` 共 11 张票，当前 01/02/03（骨架、导入存储、自选）已完成并验证，余下 8 张全是 `todo`。依赖图上 05（规则求值器）是咽喉：卡住它，06/07/08/09/10/11 全部不可执行。

原始范围（spec `docs/specs/2026-11-16-quant-p0.md` + ADR 0003）把 P0 定为「Web 配置端 + Android 预警两页」。但推送由 ntfy 承担后，手机侧「收到并立刻看一眼」已经成立，而 Android 端真正新增的能力只有「已读状态」与「预警详情页」——详情按 04 号票的备注本来就是跳浏览器。为这点增量单独维护一条 Expo/RN 构建链，是 P0 里性价比最低的一笔。

同时，剩余 8 张票一次性摊开的返工风险不均衡：04（个股详情）、09（日报）、10（调度）的价值都建立在「规则已经能求值并推送」之上，而 05/07/08 还没跑通过一次真实推送。

## 决策

1. **本迭代范围收敛为预警最小闭环**：05 规则求值器 → 07 预警列表 → 08 通知。跑通一次「收盘后算出触发 → ntfy 送达」的真实链路后，再决定其余票的去留。
2. **04 个股详情、09 日报、10 收盘后调度顺延到下一迭代**。三张票保持 `status: todo`，不降级、不删除；边界与验收标准不变。
3. **11 Android 端移出 P0，标注 P1**。ADR 0003 决策 4 关于双端分工的结论不变（Android 将来仍只做预警两页），变的只是交付时点。
4. **P0 阶段的手机侧由 ntfy 客户端承担「感知」，Web 承担全部「阅读与操作」**：没有已读状态，ntfy 客户端自身的已读即可；预警记录只在 Web 上浏览。

## 备选方案

| 方案 | 未采用的原因 |
|---|---|
| 8 票全量推进到 P0 完整落地 | 04/09/10 的价值依赖 05 已跑通；先摊开等于在没有反馈的情况下写最多的代码 |
| 先做 04 个股详情（纯展示、风险最低） | 它不推进核心链路，做完仍然无法验证「预警是否有用」这个唯一重要的假设 |
| 只做单票 05，做完再评估 | 05 单独存在时无法验证端到端，求值结果没有出口，等于半成品 |
| PWA 添加到桌面代替 APK | 省不了多少工，但保留了「多端入口」的心理负担；且 ntfy 已覆盖触达，PWA 无增量能力 |

## 后果

- **P0 阶段没有日报**，而 ADR 0002 决策 3 依赖「超出推送上限的命中项合并进当日日报」。在 09 落地前，超限命中项必须有别的去处——这是 08 实现时必须先定的口径，不能默认丢弃。
- 预警的「已读」只存在于 Web，手机上读过之后 Web 端仍显示未读；单用户自用场景可接受。
- 11 号票的 `blocked_by: [07]` 依然成立，恢复时直接可执行，不需要重新拆票。
- 若下一迭代证明最小闭环已经够用，04/09/10 可能被继续推迟——这是本决策刻意保留的选项，不是遗漏。
