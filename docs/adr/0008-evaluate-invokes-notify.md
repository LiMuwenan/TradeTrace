# 0008 求值结束后同步调用通知，不做独立轮询

- 状态：已接受
- 日期：2026-11-26
- 关联：ADR [0006](./0006-p0-scope-convergence.md)（本迭代只做 05 → 07 → 08）、ADR [0007](./0007-rule-state-event-stream.md)（事件流与 `meta.db`）

## 背景

05 负责求值写库，08 负责把预警推到手机，10 号调度将来的编排是「增量取数 → 规则求值 → 通知推送 → 日报」。但 10 号票已顺延，本迭代内不存在调度器，只有 05 的手动端点 `POST /api/v1/rules/evaluate`。

需要定的是：求值写下的 `enter` 记录，由谁、在什么时机交给通知。

## 决策

1. **求值服务在写库提交后，于同一请求内同步调用通知服务**。投递对象为本次求值产生、`event='enter'`、`replayed=0`、`pushed_at` 为空的行。
2. **通知失败不回滚求值结果，也不改变接口的成功语义**。求值写库成功即算成功，推送失败只记录该行的投递结果与原因，接口响应中单独给出推送摘要（成功数 / 失败数）。
3. **08 只提供进程内 service 接口，不新增对外端点，不做轮询**。
4. **补推靠重跑**：同一交易日重复求值时，`pushed_at` 非空的行跳过，为空的行重试，天然幂等，不需要额外的队列。
5. **10 号调度将来只需调一次求值接口**，不必再单独调推送——推送是求值的收尾阶段，不是独立步骤。

## 备选方案

| 方案 | 未采用的原因 |
|---|---|
| 08 独立轮询 `pushed_at IS NULL` 的行 | 在没有调度器的情况下要常驻一个轮询循环，等于把 10 号票的活提前做了一半且做得不完整（无失败退避、无运行记录） |
| 求值只返回待推送列表，由调用方逐个去推 | 手动端点与将来的 10 号调度要各实现一遍推送逻辑，漏写一次就是静默漏推，且两处的上限计数会各自为政 |
| 把推送做成异步任务队列 | 单用户、每日至多 50 条，引入队列与 worker 的运维成本远超收益 |

## 后果

- **求值接口的耗时包含网络调用**。单日最多 50 条推送，串行投递在最坏情况下可能阻塞几十秒，因此 ntfy 请求必须设短超时（建议 5s），超时即降级邮件，不能让一次网络抖动拖死整个求值请求。
- 推送失败后不会自动重试，要等下一次重跑该交易日（手动或将来由 10 号调度补跑）。这一点必须让用户可见——07 的列表里应能看出哪些预警尚未成功投递。
- 若将来引入失败重试队列或改成异步投递，本决策的第 1、4 条要一起改，不能只改一半。
- 求值与通知在代码上是「写库 → 收尾阶段」的关系，通知实现的异常必须被兜住，绝不允许反向影响 `rule_state_event` 已写入的记录。
