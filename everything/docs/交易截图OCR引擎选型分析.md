# 交易截图 OCR 引擎选型分析

> 场景：交易记录与复盘客户端（Expo 58 / React Native / Web 双端）  
> 输入：同花顺对账单截图（首期；雪球、腾讯自选股暂缓）  
> 硬约束：**端上离线识别、截图不上传、Android + Web 双端可用**  
> 结论先行：推荐 **PaddleOCR PP-OCRv5 mobile（检测 + 识别）经 ONNX Runtime 双端部署**；ML Kit 作为 Android 快速原型与备选；Tesseract 仅用于 Web 原型；云端 OCR/多模态大模型默认排除。

---

## 1. 结论摘要

| 角色 | 方案 | 理由 |
|---|---|---|
| **推荐主方案** | PaddleOCR mobile det + rec，ONNX Runtime（Android：`onnxruntime-react-native`；Web：`onnxruntime-web` WASM） | 中文+数字精度高、有坐标、离线、无 GMS 依赖、双端模型一致 |
| **快速验证/备选** | Google ML Kit 中文文本识别（仅 Android） | 接入简单、速度快；但仅 Android，国内 GMS 覆盖与 Expo 原生集成的风险需实测 |
| **仅原型** | Tesseract.js（Web）/ Tesseract native（Android） | 中文混排与版面能力弱，包体大，不建议作为生产主引擎 |
| **默认排除** | 云端 OCR、云端多模态大模型 | 违反“离线、不上传”硬约束；仅可作为用户显式开启的未来兜底 |
| **当前不适用** | 端上视觉大模型（3B 级） | 模型体积、内存、耗电与 Expo 集成成本不适合手机端 |

**关键判断**：截图是“数字生成的清晰文本”，不是拍照文档。识别难点不在字符本身，而在**版面重建（表格/卡片 → 行 → 字段）**与**数字校验**。因此选型不能只看 OCR 厂商宣传准确率，必须用三款 App 的真实截图做**字段级**评测。

---

## 2. 需求与约束拆解

### 2.1 输入特征

| 特征 | 对 OCR 的影响 |
|---|---|
| 中文 + 数字混排 | 需要中文识别模型；数字/字母易混淆（`0/O`、`1/l`、`5/S`、`8/B`、`6/9`、`2/Z`） |
| 清晰屏幕文本 | 字符识别难度低，传统 OCR 足够；重点是坐标与行聚类 |
| 表格（同花顺） | 需要检测框 + 行列对齐，不能只返回纯文本 |
| 表格/列表/卡片（同花顺为表格，后续券商多为列表/卡片） | 需要按表格列边界或卡片边界分组，字段标签与值配对 |
| 深色/浅色主题 | 需要亮度归一化（深色底反转为浅底深字） |
| 不同分辨率/缩放 | 需要控制输入长边，兼顾小字与速度 |
| 截图中可能有账户名等隐私 | 必须本地处理；输出前丢弃无关字段 |

### 2.2 工程约束

- **离线**：飞行模式可用，不能依赖网络。
- **双端**：Android App + Web 浏览器；不能只有 Android 方案。
- **Expo 58**：带原生模块的方案需要 Dev Client / prebuild，不能用 Expo Go；需确认 RN 0.88 与新架构兼容性。
- **包体**：模型/语言包不能无限膨胀；Web 需按需加载。
- **性能**：单张截图端到端目标 ≤ 5 秒（中端 Android）；Web 可接受首次加载较慢。
- **可测试**：解析层必须能用固定文本行 fixture 单测，不能被 OCR 引擎绑定。
- **许可**：需确认模型与运行时的开源/商业许可。

### 2.3 硬约束筛选

```
离线 + 不上传 + Android/Web
   ├─ 云端 OCR / 云端 VLM        → 排除（仅未来显式开启的兜底）
   ├─ 端上 3B 级视觉大模型        → 暂不适用（资源与集成）
   └─ 端上轻量 OCR
        ├─ ML Kit                → 仅 Android
        ├─ PaddleOCR + ONNX      → Android + Web
        └─ Tesseract             → Android + Web（精度弱）
```

### 2.4 真实样本观察（同花顺，17 张）

已收到 `everything/assets/ocr/同花顺` 下 17 张截图（均为浙商证券版式），人工查看后的关键事实：

| 观察 | 对 OCR 选型的影响 |
|---|---|
| 单一版式：浙商证券红头版，`金额/费用` | 可按固定结构解析；OCR 仍需稳定输出**坐标**，不能只返回纯文本流 |
| 表格三列、每行由三行文本组成 | 必须做行块聚类；纯文本 OCR 后处理成本高 |
| **没有股票代码，只有名称**（含 `XD` 等前缀） | 需要本地股票字典；OCR 必须准确识别中文名称 |
| 买入金额为负、卖出为正；方向文字明确 | 方向以文字为准，金额符号只作交叉校验 |
| 股息行价格列为分红参数、数量为 0 | 字段映射不能套用 `price × shares` |
| 存在 `股息红利税补缴`（负金额） | 需要支持负股息或单独字段 |
| 存在 `银行转存/转取`、`申购配号` | 必须能识别并跳过非交易行 |
| 存在深色/浅色、顶部截断 | 预处理与容错是必需项，不是可选项 |

结论：这是一个**版面重建问题 + 字段语义问题**，不是单纯“把字认出来”。因此：

- 优先选择**能返回检测框和逐行文本**的引擎；
- 解析层必须能处理负金额、非交易行与截断；
- Tesseract 这类版面能力弱的方案，生产风险明显更高；
- PaddleOCR + ONNX 的“检测框 + 识别”组合更匹配该场景。

## 3. 候选方案

### 3.1 Google ML Kit 中文文本识别

| 项 | 说明 |
|---|---|
| 平台 | Android（iOS 也可，但本项目暂不需要） |
| 运行方式 | 端上模型；可用 bundled（打包进 App）或由 Google Play 服务提供 |
| 输出 | 文本块/行 + 边框 + 可选置信信息 |
| 优点 | 接入简单、速度快、对清晰文本准确率高 |
| 缺点 | **仅 Android**；国内大量设备无 GMS，可能存在模型不可用/行为不一致；需要原生模块与 Dev Client；Web 无对应能力 |
| 适用 | Android 快速原型、备选/加速路径 |

> 关键风险不是“ML Kit 不准”，而是**设备环境**：必须在目标手机（含无 GMS 场景）实机验证 bundled 模型是否可用。

### 3.2 PaddleOCR mobile + ONNX Runtime

| 项 | 说明 |
|---|---|
| 平台 | Android + Web（同一套 det/rec 模型） |
| 组件 | 文本检测（DB）+ 文本识别（CRNN/CTC），中文识别字典 |
| 运行时 | Android：`onnxruntime-react-native`；Web：`onnxruntime-web`（WASM，可选多线程） |
| 优点 | 中文+数字精度强；有检测框，利于版面重建；开源（PaddleOCR Apache-2.0）；无 GMS 依赖；双端结果一致，便于测试与调参 |
| 缺点 | 集成成本最高：检测后处理（DB）、识别解码（CTC）、字典、预处理都要自己接；RN 原生模块与新架构兼容需验证；Web WASM 首次加载与内存需评估 |
| 适用 | **生产主方案**；尤其重视双端一致与国内设备兼容 |

补充：

- 也可评估 Paddle Lite（Android）或 Paddle.js（Web），但会形成两套运行时；ONNX 路线更利于统一。
- 模型建议用 mobile 版并做 int8 量化；以实际发布版本为准（PP-OCRv5 / v4）。
- 社区 RN 封装成熟度需先调研，不能假设“有现成库且兼容 Expo 58”。

### 3.3 Tesseract / Tesseract.js

| 项 | 说明 |
|---|---|
| 平台 | Web 用 `tesseract.js`；Android 需原生 wrapper |
| 优点 | Web 接入快、Apache-2.0、离线、中文语言包成熟 |
| 缺点 | 中文混排、小字号、表格版面准确率明显弱于 PaddleOCR；语言包十余 MB；RN 原生 wrapper 维护活跃度低；双端体验不一致 |
| 适用 | Web 原型、PaddleOCR 不可用时的临时兜底 |

### 3.4 云端 OCR / 多模态大模型

| 项 | 说明 |
|---|---|
| 代表 | 百度/腾讯 OCR、通义千问 VL、GPT-4o 等 |
| 优点 | 精度高、版面与语义理解强、无需端上模型 |
| 缺点 | **必须联网、截图离开设备**，与硬约束冲突；有成本、限流、隐私与合规问题 |
| 适用 | 未来“用户显式开启”的兜底，不作为默认路径 |

### 3.5 端上视觉大模型

| 项 | 说明 |
|---|---|
| 代表 | 3B 级视觉语言模型 |
| 优点 | 版面/语义理解强，可端上离线 |
| 缺点 | 模型数 GB、内存/耗电/发热压力大；Android 集成复杂；Expo RN 生态不支持 |
| 适用 | 当前不适用，列入长期观察 |

### 3.6 其他

- **Apple Vision**：项目暂无 iOS 端，暂不评估。
- **EasyOCR / RapidOCR（Python）**：适合服务端/桌面，不符合端上约束；其 PP-OCR 模型与后处理思路可借鉴。
- **WebView 内跑 Web OCR**：可作为 Android 原型捷径，但性能、内存、文件访问与稳定性不适合生产。

## 4. 评估模型

### 4.1 权重

| 维度 | 权重 | 说明 |
|---|---|---|
| 中英文/数字识别准确率 | 30% | 以最终**字段级**准确率为准，不只看字符准确率 |
| 版面与坐标能力 | 20% | 是否返回检测框、行/列重建是否可行 |
| 离线与隐私 | 15% | 完全本地、无网络请求 |
| 双端一致性 | 15% | Android 与 Web 是否可共用模型/流程 |
| 工程集成与 Expo 兼容 | 10% | 原生模块、新架构、构建复杂度 |
| 包体/性能/资源 | 10% | 模型大小、内存、延迟、耗电 |

### 4.2 初评矩阵

> 评分为工程判断（1–5），**不是实测结论**；必须用真实样本校准。

| 方案 | 准确率 | 版面 | 离线 | 双端 | 集成 | 资源 | 加权 | 结论 |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| PaddleOCR + ONNX | 5 | 5 | 5 | 5 | 2 | 3 | **4.50** | 推荐 |
| ML Kit（Android） | 5 | 4 | 4 | 1 | 4 | 4 | **3.85** | 备选/快速原型 |
| Tesseract | 3 | 2 | 5 | 3 | 4 | 3 | **3.10** | 仅原型 |

\* 云端与端上大模型即使加权分不低，也因硬约束/资源门槛被排除，不参与最终排序。

## 5. 分平台落地分析

### 5.1 Android

| 方案 | 可行性 | 主要风险 | 建议 |
|---|---|---|---|
| ML Kit | 高（若 GMS/模型可用） | 国内设备兼容性、Expo 原生模块、仅 Android | 做 1 天级原型验证；若目标手机稳定且准确率达标，可作为 Android 快速路径 |
| PaddleOCR + ONNX Runtime | 中 | 原生模块与新架构、预处理/后处理工作量大、模型打包 | 作为统一主方案推进；先做最小 det+rec 闭环 |
| Paddle Lite | 中 | 另一套运行时、生态与文档成本 | 若 ONNX RN 不稳定再评估 |
| Tesseract native | 低—中 | 封装维护、精度弱 | 不用于生产 |

### 5.2 Web

| 方案 | 可行性 | 主要风险 | 建议 |
|---|---|---|---|
| PaddleOCR + ONNX Runtime Web | 中—高 | WASM 加载、线程需 COOP/COEP、内存、首次耗时 | 主方案；模型按需加载并缓存；用 Web Worker 避免卡 UI |
| Tesseract.js | 高 | 中文/版面精度、语言包体积 | 原型或兜底 |
| 云端 OCR | 高 | 违反离线约束 | 默认排除 |

Web 端建议：

- 使用 Web Worker 执行推理，主线程只做展示。
- 模型文件带版本与哈希，缓存到 IndexedDB/Cache API；更新时失效旧缓存。
- 若静态托管无法配置 COOP/COEP，则按单线程 WASM 估算性能。
- Web 首次加载语言/模型较慢是已知折衷；产品文案应明确提示。

### 5.3 Expo 58 集成注意

1. ML Kit、ONNX Runtime 都需要原生模块，**Expo Go 不可用**，必须 Dev Client + prebuild。
2. 必须确认模块支持 RN 0.88 / 新架构（Fabric/TurboModules）；不支持则需找替代或自行封装。
3. 新增依赖只用 `npx expo install`；原生依赖需在 `app.json` 配置插件。
4. Web 端不涉及原生模块，但需要处理 WASM 资源打包与跨域隔离头。
5. 构建产物体积必须实测，不能只估算。

## 6. 推荐方案

### 6.1 目标架构

```
截图
 → 预处理（方向/压缩/深色反转/长边限制）
 → 文本检测（PaddleOCR DB，ONNX）
 → 文本识别（PaddleOCR rec，ONNX，中文+数字）
 → 文本行（text + box + confidence）
 → 券商模板解析（首期：同花顺；后续：雪球 / 腾讯自选股）
 → 行/列聚类与字段配对
 → 交叉校验（价格×数量≈金额、日期、方向）
 → 候选交易 → 人工确认
```

**统一模型、双端运行时**：

| 平台 | 运行时 | 模型 | 备注 |
|---|---|---|---|
| Android | `onnxruntime-react-native` | det + rec（int8） | 需 Dev Client；验证新架构兼容 |
| Web | `onnxruntime-web` | 同一套 det + rec | WASM；Worker；缓存 |
| 测试 | 纯 TS fixture | 无 | 解析/归一化不依赖引擎 |

### 6.2 为什么不是 ML Kit 作为主方案

- 仅覆盖 Android，Web 仍需另一套引擎，双端结果与调参不一致。
- 国内 GMS 环境不确定；即使 bundled 模型可用，也需要逐机型验证。
- 对“个人单用户”场景，ML Kit 完全可能是更省事的选择；因此保留为**快速原型与 Android 备选**，不排除最终采用“Android ML Kit + Web PaddleOCR”的双栈方案。

### 6.3 分阶段决策门

| 阶段 | 动作 | 决策门 |
|---|---|---|
| G0 可行性 | 用同花顺浙商版式 × 3 种场景（买入/卖出/股息）跑 ML Kit 与 PaddleOCR 最小原型 | 能否稳定输出文本行与坐标 |
| G1 精度 | 同花顺 17 张（浙商证券版式）评测字段级准确率 | 关键字段（日期/名称/方向/价格/数量/费用）≥ 95% |
| G2 体验 | 中端 Android 实测延迟、内存、包体；Web 实测首次加载与单张耗时 | 单张 ≤ 5s；包体增量可接受 |
| G3 选型 | 通过则定 PaddleOCR；若仅 ML Kit 达标且目标机型确定可用，则可改双栈 | 形成书面决策记录 |

### 6.4 降级与兜底

- OCR 引擎失败 → 允许手动录入，不阻塞用户。
- 字段置信度低 → 留空并高亮，不强猜。
- 未来如确需服务端兜底：默认关闭，用户显式开启并知情后才上传；另行评审隐私与实现。

## 7. 工程实现要点

### 7.1 预处理

- 按 EXIF 校正方向；长边限制在合理范围（如 1600–2000px，实测调优）。
- 深色主题：先判断平均亮度，必要时反转为浅底深字。
- 轻度对比度增强；避免过度二值化破坏抗锯齿数字。
- 保留原图哈希用于去重与审计，不保留原图长期存储。

### 7.2 检测与识别后处理

- DB 检测：阈值化、连通域/轮廓、框扩张、NMS；输出四点框。
- 识别：CTC 解码、字典约束、置信度；空结果与低置信标记。
- 行聚类：按框中心 y 排序，以中位框高为容差聚行；再按 x 分列。
- 表格：先识别表头列边界，再把每行文本分配到列；跨行备注单独处理。
- 卡片：以卡片视觉边界或“股票名/方向”锚点分组，字段标签后取值。

### 7.3 数字与日期校验

- 正则 + 语义双重校验：价格、数量、金额、费用、日期、时间。
- 金额校验：`|价格 × 数量 − 成交金额|` 在费用容差内；不一致则标记待确认。
- 千分位、小数位、负号、`+/-`、`元/股` 等单位统一清洗。
- 易混字符：对数字字段做字符集约束（只允许数字/小数点/负号），降低 `O→0`、`l→1` 之类错误。

### 7.4 置信度与阈值

- 检测置信度与识别置信度分开记录；最终字段置信度取组合值。
- 不同引擎的置信度不可直接比较，阈值需按引擎分别校准。
- 建议：高置信自动勾选但**仍可编辑**；中置信默认勾选并高亮；低置信默认不勾选。
- 任何情况下都不自动入库。

### 7.5 性能与资源

- 模型 int8 量化；复用推理 Session，避免每张图初始化。
- 限制并发（1–2 张），批量时逐张处理并显示进度。
- Web 用 Worker；注意 WASM 内存与线程数；低端机降级为单线程。
- 统计 p50/p95 延迟、峰值内存、失败率，写入本地诊断日志（不含图片内容）。

### 7.6 许可与合规

- PaddleOCR：Apache-2.0；模型许可需随版本确认。
- Tesseract：Apache-2.0；`chi_sim` 训练数据许可需确认。
- ML Kit：受 Google 服务条款约束，需确认商用/分发要求。
- 上线前整理第三方许可清单，随 App 提供声明。

## 8. 评测方法（真实样本到位后执行）

### 8.1 样本集

| 维度 | 要求 |
|---|---|
| 券商 | **同花顺 17 张（已提供）**；雪球、腾讯自选股暂缓 |
| 版式 | 浙商证券对账单版式（`金额/费用`、带符号金额） |
| 场景 | 买入、卖出、股息入账、股息红利税补缴 |
| 非交易 | 银证转账、申购配号（用于验证可跳过） |
| 主题 | 深色、浅色 |
| 质量 | 原图、压缩图、小字号、顶部/底部截断各若干 |
| 脱敏 | 账户名、资金、身份证等全部遮蔽 |

### 8.2 指标

| 指标 | 说明 |
|---|---|
| 字段精确匹配率 | 日期、代码、名称、方向、价格、数量、手续费、金额逐字段比较 |
| 行级完整匹配率 | 一行所有关键字段都正确 |
| 字符错误率 CER | 辅助定位引擎问题，不作为唯一结论 |
| 关键字段准确率 | 价格/数量/方向/日期加权，目标 ≥ 95% |
| 延迟 | 单张 p50/p95；批量总耗时 |
| 资源 | 峰值内存、包体增量、耗电（定性） |
| 失败模式 | 哪些版式/主题/字号失败，是否可被人工快速修正 |

### 8.3 评测流程

1. 固定样本与标注（JSON 期望值）。
2. 同一预处理参数下分别跑 ML Kit、PaddleOCR、Tesseract。
3. 输出字段级对比表与混淆案例。
4. 按券商分别统计，避免某一家拉高整体。
5. 根据结果更新权重与阈值，形成最终选型记录。

## 9. 风险与缓解

| 风险 | 等级 | 缓解 |
|---|---|---|
| PaddleOCR RN 集成成本超预期 | 高 | 先做最小闭环；评估社区封装；必要时 Paddle Lite 或双栈 |
| ML Kit 在无 GMS 设备不可用 | 高 | 目标机型实机验证；优先 bundled 模型；不作为唯一方案 |
| Web WASM 性能/加载差 | 中 | Worker + 缓存 + 进度提示；允许 Web 导入为次要能力 |
| 深色/小字号识别率下降 | 中 | 亮度归一化、放大策略、低置信高亮 |
| 数字混淆（O/0、l/1） | 中 | 字段字符集约束 + 金额交叉校验 + 人工确认 |
| 模型/语言包体积过大 | 中 | int8 量化、按需加载、构建实测 |
| Expo 新架构不兼容 | 中 | 选型前查兼容矩阵；无法兼容则换运行时或自行封装 |
| 许可不清 | 中 | 上线前整理第三方许可清单 |
| 同花顺 UI 改版/字段错位 | 高 | 表头锚点 + 列坐标校验；模板版本化；字段不确定置空 |
| 截图无股票代码 | 高 | 本地股票字典 + 名称归一化 + 手动选择兜底 |
| 截断行/状态栏干扰 | 中 | 裁剪表格区域；不完整行不自动勾选 |
