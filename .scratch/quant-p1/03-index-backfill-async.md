## 要做什么

修掉「加入指数要等很久、看起来像没反应」和「一次拉 20 年会被数据源断连」两个问题，并让指数取数在进程内串行（baostock 是全局 socket，并发会互相踢会话）。

## 验收标准

- [x] `POST /watchlist` 加入指数**立刻返回**，`item.historyPending = true`；回补在后台线程里跑
- [x] 回补按 5 年分段（`CHUNK_YEARS`），每段单独入库；某段失败保留之前的进度并停下
- [x] 单段失败自动重试一次（`CHUNK_RETRIES`），仍失败则返回错误文本
- [x] 进程内所有指数取数走同一把可重入锁，并发调用峰值只有 1 路
- [x] 新增 `POST /api/v1/stocks/{code}/history`：可对已入库的指数续补缺口，只对指数开放（股票 404）
- [x] 自选条目带 `historyPending` / `historyError`；详情响应带 `history` 运行态
- [x] 前端：加入按钮有「加入中…」且一次只加一个；清单里指数显示「回补中…」或「补数据」，补完自动刷新
- [x] 流水线指数阶段的首次补数也走同一套分段逻辑

## 备注

- 用户反馈的三个现象：① 第一次点「加入」没反应、要点两次（同步拉 20 年 + 前端无 pending 状态）；② 连续加入两个指数时并发取数（会互相踢 baostock 会话）；③ 拉历史时取到 2014 年连接被关。
- ③ 的直接原因是**单次区间跨度过大**（2006→今天约 5000 行），已改为 5 年一段；失败点的进度照常入库，下次从最后一条之后续补。
- 顺带修正详情页 404 文案：不再让人「移除后重新添加」，改为指向自选里的「补数据」。
- 已知取舍：回补是**进程内**后台线程，进程重启会丢运行态（数据已入库的部分不丢）；重进页面后状态从「没有 pending」开始，未补完的缺口靠「补数据」或下一次流水线补。

**实施记录**（2026-11-27）：

- `_FETCH_LOCK` 用 `threading.RLock`：`ensure_history` 会套着锁调 `sync_range`，普通 Lock 会自锁死。
- 后台运行态键是 `数据目录|代码`，避免同一进程里不同配置（测试的 tmp 目录）互相覆盖状态。
- 失败即停而不是继续下一段：后续段依赖同一条连接，继续只会重复同一个错误，还掩盖真实失败点。
- 本地实测：`sh.000001`、`sh.000300` 各 5076 行，2006-01-04 ~ 2026-11-26，说明断连是暂时性的——旧代码重试（再次点加入）也能补全，只是过程完全不可见。
