## 要做什么

把前面各票串成每天自动运行的流水线，用户不需要每天手动点任何按钮，同时保留手动补跑某个交易日的能力。

## 验收标准

- [x] 每个交易日收盘后自动执行：增量取数 → 规则求值 → 通知推送 → 生成并投递日报
- [x] 非交易日不执行，也不产生空的日报或预警
- [x] 维护增量游标：记录最后一个成功入库的交易日，下次从其后开始
- [x] 某天失败时留下缺口记录，次日自动尝试补齐；缺口可手工触发补跑
- [x] 可手动指定任意交易日重跑整条流水线，重复执行不产生重复预警
- [x] Web 运行记录页展示：每次运行的日期、各阶段耗时、成功/失败、失败原因
- [x] 任一阶段失败不影响已完成的阶段（例如取数成功但通知失败，取数结果仍保留）

## 备注

**每日取数调用量**：全市场日线一次 + 当日除权清单一次，共两次批量调用；逐标的循环取数在设计上被排除。

**数据缺口**：缺口是指「应为交易日但未成功入库」的日期，不是指单只标的停牌。停牌是正常数据，不算缺口。

**不做**：盘中实时求值、交易日历对接（是否交易日以数据源返回的当日数据是否为空来判定）。

**排期**：2026-11-26 起本票顺延到下一迭代，且依赖的 09 日报已同时顺延，开工顺序需在 09 之后重排。见 ADR `0006-p0-scope-convergence.md`。在此之前「每天自动跑」由手动触发求值 + 推送代替。

**实施记录**（2026-11-26）：流水线在 `app/services/pipeline.py`（`run` / `catch_up` / `scheduled_run`），定时器在 `app/services/scheduler.py`（`DailyScheduler`，进程内 `asyncio`，`TICK_SECONDS = 30`），运行记录存 `app/storage/pipeline_store.py`（`pipeline_run` / `pipeline_stage` / `pipeline_cursor` 三张表）。接口 `GET /pipeline/runs`、`POST /pipeline/run`，前端 `PipelineRunsPage.vue`（侧栏「运行记录」）。配置新增 `schedule.enabled`（默认 `false`）与 `schedule.time`（默认 `15:30`，正则校验 `HH:MM`，非法即启动失败）。

**五处实现判断**：

- **定时器不引 cron**。服务本身就是长期运行的局域网进程，进程内一个 `asyncio` 任务就够，少一个部署依赖；到点后把同步流水线丢进 `asyncio.to_thread`，不阻塞 API。代价是重启会丢「今天已跑过」的内存标记，当天可能再跑一次——流水线本身幂等（事件唯一键、已投递日报不改写），重跑安全。
- **先标记再执行**。`_execute` 一开始就写 `_last_triggered`，失败也计为「今天已触发」。否则每 30 秒重试一次，会把数据源打爆；失败留给次日的 `catch_up` 覆盖。
- **「通知」不单列阶段**。ADR 0008 已让求值末尾同步推送，再单开一步会把同一批预警推两遍。所以阶段只有 `ingest` / `evaluate` / `report`，推送条数记在 `evaluate` 的 detail 里。
- **缺口不建表**。「游标之后的工作日」加上「运行记录里 `status='failed'` 的日期」就是全部缺口，多一张表只会多一处不一致。首次运行（游标为空）不回溯历史，只试终点日，避免刚部署就发起上百次抓取。
- **非交易日与失败分开记**。数据源返回为空抛 `NoMarketDataError`（`schema.py` 新增，`RealtimeSource.load` 抛出），流水线记 `skipped` 并提前返回：不算失败、不推进游标、不生成空日报。真正的故障仍记 `failed`。
