## 要做什么

06 号票的「停用 / 改参数先写一条 exit 收尾」与 05 号的「启用前静默回放」在同一个键上打架：如果条件在停用期间一直满足，重新启用后库里的最后一条事件仍是那条 `exit`，于是次日求值会误判为「刚由假变真」，推出一条重复预警。本票修掉这个状态错位。

## 现状（代码事实）

1. `rule_store.close_states`（`app/storage/rule_store.py`）把收尾的 `exit` 记在**该标的该规则最后一条事件所在的 `trade_date`**（也就是 enter 那天），只是 `id` 更大：

   ```python
   trade_date=last_event(conn, code, rule_id)["trade_date"]
   ```

2. `current_state` / `last_event` 用 `ORDER BY trade_date DESC, id DESC` 取最后一条，所以同日里 id 更大的 `exit` 胜出 → 当前态被判为「未触发」。
3. 重新启用时 `rule_eval.replay_rule(until=今天)` 从头重放。当它重放到 enter 那天时，`record_event` 因为唯一键 `(code, rule_id, trade_date, event)` 冲突而**跳过写入**（返回 `False`），但回放内部的推进状态仍记为「已进入」。
4. 于是：回放不再写新的 `enter`，库里最后一条仍是那条收尾 `exit`，`current_state` 仍是 `exit`。次日正常求值看到「状态 exit + 条件仍成立」，产生一条 `enter` → 重复预警。

**触发条件**：某标的在停用（或改参数）时处于触发态，且条件在停用期间**持续满足**。条件中间断开过、或在停用期间先解除再满足的标的都不会踩到。

这与 ADR 0007「一次回放会炸出百条通知」要防的正是同一类假预警，只是这次只炸一条，更隐蔽。

## 候选方案（择一，写进票面再动手）

- **A. 收尾 exit 记在停用/改参数当天**，而不是原 enter 当日。语义更准确，但回放时仍需要知道「这天之后条件是否继续满足」，单靠改日期解决不了第 3、4 步的状态错位。
- **B. 启用回放结束后校正当前态**：若回放算出的当日状态仍是「触发中」，且该标的最新事件是 `reason in ('rule_disabled', 'rule_changed')` 的 `exit`，则删掉这条收尾 `exit`（或补一条 `replayed=1` 的 `enter`），让 `current_state` 回到真实状态。改动只在启用路径上，波及面最小。
- **C. 调整 `record_event` 的去重规则**，让「已存在同键 `replayed=1`，现在要写 `replayed=0`」这类写入不被丢弃。会把唯一键语义搞复杂，不推荐。

A 与 B 不互斥，A 可以单独作为「事件语义修正」先做。

## 验收标准

- [ ] 停用前处于触发态、停用期间条件持续满足的规则，重新启用后次日求值**不产生** `enter` 事件
- [ ] 停用期间条件先解除后又满足的规则，重新启用后仍能正常产生一条 `enter`（不能因为修了这个而漏真预警）
- [ ] 改参数（`rule_changed` 收尾）后重新求值的行为同样正确
- [ ] 现有 06/05 的测试全绿，新增用例覆盖上述两种时序

## 备注

发现于 10 号票上线后的双轴审查（Spec 轴，条款 06「回放结束后状态与历史触发次数即为真实值」与 ADR 0007）。

**同族待定项**：规则列表的「最近触发时间」（`rule_store.last_enter_dates`）只统计 `replayed = 0`，因此新建规则回放出历史触发后列表仍显示「—」。列名叫「最近触发」而非「最近提醒」，与 ADR 0007「历史触发即为真实值」的口径要不要统一，请与本票一并定，未定之前不改。
